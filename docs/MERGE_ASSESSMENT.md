# PTT AutoPost 與 PTT 登入小幫手（PTTLOGIN）合併評估報告

評估日期：2026-10-21　｜　性質：評估，未修改 PTTLOGIN 任何檔案　｜　結論先看第 1 節

## 1. 結論

| 項目 | 結論 |
|---|---|
| 技術上能否合併成單一程式 | **可以，但不建議現在做**。需把 C# 程式用 Python 重寫（約 2,800 行核心＋2,100 行介面），且「PTTLOGIN 現有功能不變更」的要求在重寫下無法保證。 |
| 與 PTT AutoPost 既定原則是否衝突 | **有衝突**。AutoPost 的設計原則是「不自動登入、不儲存密碼」；PTTLOGIN 的本質正好是「排程自動登入＋保存帳密」。合併等於修改這兩項原則，需使用者明確決定。 |
| 建議方案 | **方案 A（已採用）**：兩程式維持獨立，AutoPost 內提供入口啟動 PTTLOGIN。之後若仍想合併，再做方案 C（見第 5 節）。 |

## 2. 兩個專案現況

| | PTT AutoPost | PTTLOGIN（PttAutoLogin） |
|---|---|---|
| 語言／框架 | Python 3.12、PySide6（Qt6） | C#、.NET 9、WinForms |
| 規模 | 約 5,600 行（含測試與工具） | 核心約 2,756 行、介面約 2,140 行、測試約 1,516 行（77 項測試） |
| 發行形式 | 單檔 EXE，約 54 MB | 自包含單檔 EXE，約 113 MB |
| 連線方式 | wss://ws.ptt.cc/bbs（Origin: term.ptt.cc） | 同一端點、同一標頭 |
| 主要功能 | 擷取新聞、產生 PTT 格式、草稿、簽名檔、看板、把內容輸入到終端機（不送出） | 依日／週／月排程自動登入、重試、保留連線 N 分鐘後登出、帳號統計、登入歷史、開機自動啟動、系統匣 |
| 帳密處理 | 只在使用者輸入時使用，**不儲存、不寫入記錄** | 以 Windows DPAPI（目前使用者範圍）加密存檔 |
| 使用者資料 | `data/`、`logs/`、`config/`（SQLite＋JSON） | `Data/`（settings、history、stats、credentials.dat）、`Logs/` |

兩者重疊的部分：WSS 連線、Big5 解碼、畫面狀態判斷（登入提示、重複登入、按任意鍵）、系統匣。重疊的是「概念」，不是可共用的程式碼，因為語言不同。

## 3. 合併方式比較

| 方案 | 作法 | 工作量 | 風險 | 「現有功能不變」 | 判斷 |
|---|---|---|---|---|---|
| **A. 啟動入口（已做）** | AutoPost 設定頁與系統匣選單加「開啟登入小幫手」，PTTLOGIN 以獨立程式執行 | 小（半天內） | 極低 | **完全保證**（沒動 PTTLOGIN） | 建議先用 |
| B. 用 Python 重寫併入 | 把排程、登入、統計、歷史、DPAPI 等全部改寫成 Python | 大（估 3–5 個工作天含測試移植） | 高：行為差異、需重做 77 項測試的對應、DPAPI 資料格式要相容 | 難以保證，需逐項對照驗收 | 不建議現在做 |
| C. 共用程序／介面整合 | 保留 C# 程式，AutoPost 與它透過本機檔案或命名管道溝通，在同一視窗只顯示 AutoPost 分頁 | 中 | 中：進程間協定、版本相容、兩套打包 | 可保證核心不變 | 若想要「看起來是一個程式」再考慮 |
| D. 把 AutoPost 改寫成 C# | 以 .NET 重做 AutoPost | 很大 | 很高 | 不適用 | 不建議 |

## 4. 合併時必須處理的風險

1. **安全原則衝突**：若把自動登入併入 AutoPost，就必須同時決定 AutoPost 是否允許「儲存帳密」與「無人值守登入」。這會推翻目前文件與測試中的「不儲存密碼、不自動登入」承諾，記錄脫敏規則也要重新定義。
2. **同帳號重複登入**：兩個功能都會用同一個帳號連線。PTTLOGIN 登入後會保留連線約 10 分鐘（設定值，可到 120 分鐘），期間 AutoPost 再登入會遇到「重複登入」提示。AutoPost 目前的處理是回答 `n` 並停止，PTTLOGIN 的策略是不踢線。合併後要定義誰優先、是否共用同一條連線。
3. **憑證格式**：DPAPI 加密檔 `credentials.dat` 在 Python 端可用 Windows API 讀取，但必須維持「使用者範圍」與相同的分隔格式，否則現有帳密會失效，使用者要重新輸入。
4. **資料遷移**：`settings.json`、`history.json`、`accountstats.json`、`totalcount.json` 要保持相容，否則歷史紀錄與累計次數會遺失。
5. **打包體積與啟動**：合併為單一 Python EXE 後可省下約 113 MB 的 .NET 自包含執行檔，這是合併的主要好處之一；但若採方案 C，兩套執行檔都要隨附。
6. **背景常駐**：PTTLOGIN 需要常駐並依排程執行。AutoPost 已新增系統匣，但「開機自動啟動」、「單一執行個體」、「排程喚醒」在 Python 端都要另外實作與驗證。
7. **未在真實登入環境驗證的部分**：AutoPost 對登入後畫面（標題提示、編輯畫面）的判斷標記尚未在真實 PTT 驗證；合併前不應讓排程登入與手動輸入共享同一套未驗證的狀態判斷。

## 5. 建議路線

1. **現在（已完成）**：方案 A。AutoPost 設定頁有 PTTLOGIN 路徑欄、「瀏覽」與「開啟登入小幫手」按鈕；系統匣右鍵選單也有同樣入口。預設路徑為 `D:/Claude/PTTLOGIN/release/PttAutoLogin.exe`，可自行更改。PTTLOGIN 的帳密與排程仍由它自己管理，AutoPost 不讀取也不保存。
2. **觀察一段時間**：確認實際使用上是否真的需要「同一視窗」。若只是怕開兩個程式麻煩，方案 A 加系統匣已足夠。
3. **若仍要整合**：優先選方案 C（保留 C# 核心不動，只整合入口與狀態顯示，例如在 AutoPost 顯示 PTTLOGIN 的最近登入結果）。只有在決定接受「AutoPost 也儲存帳密與排程登入」時，才進行方案 B，且要先做以下準備：
   - 先寫下新的安全設計（帳密儲存、記錄脫敏、重複登入策略）並由你確認。
   - 先把 PTTLOGIN 的 77 項測試列為 Python 版的驗收清單，逐項對照。
   - 先在不影響現有 EXE 的前提下平行開發，通過後才取代。

## 6. 需要你決定的事項

- 是否接受 AutoPost 日後儲存帳密、做排程自動登入（目前不接受）。
- 若要單一程式，優先考量是「減少檔案大小」還是「單一視窗」。前者適合方案 B，後者適合方案 C。
- 同帳號重複登入時的優先順序（手動操作優先，或排程優先）。

本報告不構成財務或法律建議；涉及帳號安全與服務條款（例如自動登入是否符合站方規範）請自行確認。
